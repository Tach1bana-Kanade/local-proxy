# 网站自动分类与一键确认方案

日期：2026-09-22。状态：设计方案，尚未实现；依据当前源码提交 `7a435a1`。

## 目标与推荐路线

用户不再自行判断网站是否属于海外网站。工具展示“建议直连 / 建议代理 / 暂无法判断”、判断依据和适用域名，用户点击“确定并记住”后生效，并可随时覆盖或撤销。

推荐保留 SwiftUI、Quickcat 和 PAC 架构，新增本地分类器。先完成输入网址后的自动推荐，再增加浏览器扩展，实现访问新网站时自动出现建议。第一阶段解决人工判断，第二阶段解决手动输入。

网站运营方所在地、域名后缀、服务器 IP 所在地和适合的网络出口是不同信息。不要把“海外 IP”直接等同于“必须代理”，也不要承诺准确识别网站国籍。界面以网络建议为主；IP 地域仅作为可选参考，并标明不确定性。

## 当前代码与约束

- `Sources/ProxyAppsCore/ManagedWebsite.swift`：现有规则只有域名和 enabled，没有显式直连、分类来源和确认状态。
- `Sources/ProxyAppsCore/PACGenerator.swift`：白名单命中走 Quickcat HTTP `127.0.0.1:21081`，其余直连。
- `Sources/LocalProxyApp/ProxyAppsController.swift`：添加网站即保存，适合拆成“分析、预览、确认保存”。
- `Sources/LocalProxyApp/PACServer.swift`：仅提供 `/proxy.pac`，接收到的是浏览器取配置的请求，不是每次访问网站的请求。
- 正式 App 使用 `ProxyAppsCore`，没有运行历史 `LocalProxyCore` / Mihomo / TUN 原型。
- Chromium 应用的“代理启动”会注入固定代理参数；这种启动方式与按域名分流有冲突，必须明确区分。

PAC 在浏览器内部执行，不能直接弹出 SwiftUI 窗口或可靠地通知主应用新域名。不要通过 PAC 中的特殊 DNS 请求上报浏览记录。遵循系统 PAC 的应用才能使用这一分流方式，它不能覆盖所有进程、UDP 和所有浏览器网络行为。

## 用户流程

### 第一阶段：输入网址，自动推荐

1. 粘贴网址，自动提取、标准化域名，复用现有输入校验。
2. 查询本地规则库；未知域名按需补充检测。
3. 显示建议，例如：`example.com · 建议代理 · 规则库命中 · 包含子域名`。此例仅展示界面格式，并非该域名的真实分类。
4. 主按钮“确定并记住”；次要操作“改为直连 / 改为代理 / 暂不处理”。确认前不修改该网站的持久规则。
5. 保存后刷新路由规则，显示“配置已更新”。实际新请求是否采用新配置须经过浏览器验证；必要时提示重新加载页面。

规则页提供“代理、直连、待判断”分类，展示判断依据、来源版本、最后检测时间，以及人工修改标记。重复添加时进入已有记录，不重复弹窗。

### 第二阶段：访问时自动发现，只需确认

浏览器扩展监听顶层导航，将 hostname 通过 Native Messaging 发给本机分类器，显示扩展徽标或应用中的待确认卡片。确认后保存规则并提供重新加载入口。

先适配 Chrome / Edge，Safari 单独适配和验证。不默认扫描历史记录，不发送完整 URL、参数、Cookie 或页面内容。扩展仅跟踪当前导航，默认不处理隐身窗口；同域名请求合并，暂不处理的建议设置冷却时间。

`webNavigation` 是观察接口，不能暂停请求等待确认。新域名确认前延续原有默认直连，因此第一次请求可能失败；点击确认后重试。若未来要求“首次请求也绝不直连”，需要额外的浏览器代理控制或本地转发网关和独立的拦截策略，不能由现有 PAC + 导航观察承诺。

第一版扩展只负责发现和确认，系统 PAC 继续由 App 管理，避免出现两个互相覆盖的代理配置来源。Native Messaging host 限定允许的扩展 ID，并校验消息格式、域名和消息大小。

## 自动分类逻辑

### 建议的判断顺序

1. **本地与保留地址保护**：localhost、局域网、链路本地、IPv6 本地地址直连，避免向外部服务查询内部域名。
2. **用户已确认规则**：人工设置优先；同一层级精确规则优先，更具体的子域名规则优先。
3. **本地规则库**：匹配可直连列表与代理列表，输出来源和规则版本；同一精度的相反命中标记冲突，不偷偷选一个。
4. **未知域名检测**：比较明确直连和明确经过 Quickcat 的连接结果，提供带时效的建议。
5. **仍不确定**：保留“待判断”，允许采用当前直连策略或由用户指定代理，不伪装成确定结论。

规则库候选为 Loyalsoldier 的 direct-list / proxy-list，或基于 v2fly domain-list-community 定制的数据。它们是路由分类资料，不是网站国籍数据库。接入前核对所选数据的格式、来源许可与再分发要求，保留归属信息。

首版支持精确域名、域名后缀两种已验证语义。不能把 `full:`、`regexp:` 等规则标记直接当成域名字符串；不支持的条目要统计并展示，不能无声地变成错误规则。不要擅自将所有输入扩展到最后两段域名；需要站点级归并时使用 Public Suffix List，避免扩大到共享托管域名。

### 连通性检测与误判控制

- 使用独立、无 Cookie 的临时会话，明确禁用直连探测的系统代理；代理探测显式指向 Quickcat，避免两次探测实际走同一条路。
- DNS、TCP、TLS、HTTP 分层记录结果。TCP 成功或代理端口开放不代表网站业务可用，403 / 429 / 登录验证也不直接等同于网络被阻断。
- 未知域名进行有总超时的有限检测，例如总预算 5 秒、最多 2 次尝试；双通路都正常时偏向直连，直连持续失败而代理成功时建议代理，均失败时提示无法判断。
- 不仅凭一次速度差或一次超时改规则。网络切换时使探测缓存失效；人工确认不因规则库更新或一次失败被覆盖。
- HTTPS 校验证书；不访问输入网址的路径或查询参数。使用根路径的小请求，不下载完整网页，不自动重放用户登录或业务请求。
- DNS 解析结果和重定向都做私网/保留地址检查，避免借探测服务访问内网。已明确要求代理的域名不再自动尝试直连探测。
- GeoIP 可作为后续辅助功能，首版不依赖在线 IP 归属 API，避免将访问域名交给额外第三方，也避免 CDN、多地域解析导致的错误归类。

## 执行规则与持久化

推荐新增带版本号的路由配置，保存以下信息：

| 字段 | 用途 |
| --- | --- |
| domain / match | 精确域名或包含子域名的规则 |
| action | direct / proxy |
| enabled | 是否参与路由，不把“停用”解释为显式直连 |
| source / reason / rulesetVersion | 用户选择、规则库、探测，以及依据 |
| confirmedAt | 用户确认时间 |
| probeExpiresAt | 探测结果有效期；不等于用户规则到期 |

建议结果与已生效规则分别存储。迁移旧数据时，已启用条目保持代理，停用条目仍停用；保留 ID，不改变原有行为。失败时恢复旧内存和磁盘状态。

PAC 执行顺序：本地保护 → 已确认规则（精确/更具体者优先）→ 默认 DIRECT。显式直连规则可以覆盖较宽的代理规则。第一版规则库只参与推荐，不直接将整套远程列表变成已生效规则，保证“确认后生效”。

以后可增加“信任规则库、自动处理已知网站”的独立开关：启用时展示影响范围并一次确认；未知域名仍进入待判断。关闭开关后恢复仅使用已确认规则。

代理规则仅返回 `PROXY 127.0.0.1:21081`，不追加 `DIRECT` 作为静默回退。这仅约束 PAC 正常加载且客户端遵守规则时的行为；PAC 服务不可用或客户端绕过 PAC 的情况必须另行验收，不能宣称是全系统防泄漏保证。

为 Chromium 增加独立的“按网站规则启动”模式，使用经过验证的 PAC 启动配置，不能同时注入固定 `--proxy-server` 或全部流量的代理环境变量。保留现有“全部代理启动”能力并明确标注作用范围。非 Chromium 应用继续按其实际支持能力处理。

## 代码落点

| 模块 | 工作 |
| --- | --- |
| ProxyAppsCore | 新增 RouteRule、RouteSuggestion、DomainClassifier、规则解析与纯函数匹配 |
| ProxyAppsCore/PACGenerator.swift | 显式直连、精确匹配、子域名优先级，分类与 PAC 语义一致 |
| LocalProxyApp | 新增 RuleSetStore / RuleSetUpdater / ConnectivityProbe，异步执行、取消旧分析结果 |
| ProxyAppsController.swift | 分析→预览→确认事务，持久化失败回滚，旧数据迁移 |
| ProxyAppsContentView.swift | 建议卡片、来源说明、确认按钮、手动覆盖与待判断列表 |
| PACServer / SystemPACManager | 预编译并原子替换 PAC 内容，处理配置版本与浏览器缓存，保留恢复机制 |
| ProxyAppsManager / 启动参数模块 | 分离按网站规则启动和全应用代理启动 |
| 后续浏览器扩展与 native host | 自动发现顶层域名、合并提示、确认与刷新入口 |

PAC 热路径不执行主动测速或在线 GeoIP 查询。若未来启用完整规则库自动路由，使用预编译查找结构，避免每个请求线性扫描大量规则。

规则库在本地缓存并随应用启动按时间间隔检查更新，不需要额外系统定时任务。通过 HTTPS 下载到临时位置，校验格式、大小、条目数量、重复冲突及版本后原子切换；失败继续使用上一版本。配套哈希用于完整性检查，不把同一来源的哈希误称为独立的可信签名。

PAC 版本切换须同时兼容服务路由和恢复快照：现有服务只识别精确 `/proxy.pac`，不能只在 URL 后加版本参数而不改服务器解析和恢复逻辑。浏览器可能缓存 PAC，需分别测试刷新、已有连接与重启行为。

## 分阶段交付与验收

1. **分类基础**：规则模型、旧数据迁移、规则库解析、优先级和显式直连。
2. **一键确认**：输入网址自动分析，展示原因，确认后持久化并更新 PAC；全程可撤销。
3. **未知域名补充检测**：直连/代理对比、取消与超时、网络切换缓存失效。
4. **自动发现**：浏览器扩展、Native Messaging、去重与冷却、重试流程。

验收用固定测试夹具验证推荐结果，不用不断变化的真实网站作为单元测试依据。重点覆盖：

- 直连/代理/未知/冲突四种分类，以及恶意近似域名 `notexample.com` 不命中 `example.com`。
- 更具体的直连规则覆盖父域代理规则；旧 enabled=false 不转为强制直连。
- 确认前规则不变；人工覆盖优先；写入、迁移、规则更新失败可恢复。
- 双路均失败、证书失败、403 / 429、Quickcat 关闭、网络切换不导致误报“海外网站”。
- 执行生成的 PAC JavaScript，与 Swift 分类/匹配结果交叉验证。
- Safari / Chrome 的真实直连与代理出口、PAC 缓存、启动模式冲突和退出恢复单独人工验收。
- 扩展新域名只提示一次，默认不收集隐身与历史数据，确认后可重试首次失败请求。
